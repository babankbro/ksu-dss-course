# 20. การจูนประสิทธิภาพคิวรี OLAP (Performance Tuning)

เมื่อลูกบาศก์ข้อมูลใหญ่แตะระดับล้านล้านบรรทัด ต่อให้ฮาร์ดแวร์จะแรงแค่ไหน ถ้าการจูน (Tuning) ไม่ดี คิวรีก็อาจใช้เวลารันเป็นชั่วโมง วิศวกรข้อมูลจึงต้องใช้ 3 ท่าไม้ตายในการรีดความเร็ว OLAP

## 20.1 Materialized Views (มุมมองที่ถูกสร้างเป็นรูปธรรม)
* **ปัญหา:** คิวรี `SUM(ยอดขาย)` จัดกลุ่มตาม `(ภูมิภาค, เดือน)` ถูกรันบ่อยมากบน Dashboard แดชบอร์ดมีคนเปิด 10,000 ครั้ง ฐานข้อมูลก็ต้องบวกเลขสิบล้านบรรทัดใหม่ 10,000 รอบ (ซ้ำซากและเปลือง CPU)
* **ทางแก้:** สร้าง Materialized View 
* **การทำงาน:** ฐานข้อมูลจะแอบรันคิวรีนี้ไว้ล่วงหน้า แล้ว **บันทึกผลลัพธ์ (ก้อนเล็กๆ)** เซฟลงฮาร์ดดิสก์เป็นตารางจริง
* พอมีคำขอมาใหม่ ระบบจะชิ่งไปตอบจากตารางเล็กนี้ทันที (ตอบกลับในหลักมิลลิวินาที)

## 20.2 Result Caching (การจำคำตอบ)
* ในขณะที่ Materialized View คือการปั้นตารางใหม่ Caching คือการ **"จำผลลัพธ์ล่าสุดไว้ใน RAM"**
* **กลไกอัจฉริยะ:** 
  - CEO คนแรกเข้าออฟฟิศ 8 โมงเช้า เปิด Dashboard สั่งรันคิวรีสุดโหด ระบบใช้เวลา 10 วินาที
  - ระบบจะจำคำตอบนี้ไว้ใน Cache
  - 8:05 น. ผู้จัดการอีกคนเปิด Dashboard หน้าเดียวกันเป๊ะ ระบบจะไม่บวกเลขเลย แต่คว้าคำตอบจาก Cache โยนให้ทันที (0.1 วินาที!)
* **ข้อจำกัด:** ทันทีที่มีข้อมูลยอดขายไหลเข้ามาใหม่ Cache ก้อนนี้จะถือว่า "บูด (Stale)" และถูกระบบลบทิ้งทันที

## 20.3 Partitioning และ Partition Pruning (การหั่นเค้กและการเล็มส่วนเกิน)
* **Partitioning:** คือการแบ่งไฟล์เก็บข้อมูลออกเป็นโฟลเดอร์ตามวันที่ (เช่น วันละโฟลเดอร์)
* **Partition Pruning:** เมื่อผู้ใช้งานกด Filter บนหน้าจอว่า "ขอดูยอดขายเฉพาะเดือนพฤษภาคม 2026"
  - OLAP Engine จะทำหน้าที่เป็นเหมือนบรรณารักษ์ มันจะหยิบเฉพาะโฟลเดอร์ของเดือน "พฤษภาคม" ออกมาคำนวณ
  - และ **เตะโฟลเดอร์ของเดือนอื่นๆ (ม.ค. - เม.ย.) ทิ้งออกไปจากวงจรการคำนวณทันที (Pruning)**
  - การทำเช่นนี้ช่วยลดข้อมูลขยะที่ต้องอ่านจากฮาร์ดดิสก์ได้กว่า 90%

ความสามารถในการจูนทั้ง 3 ข้อนี้ คือคุณสมบัติสำคัญที่แยก Data Warehouse ระดับโลก ออกจากฐานข้อมูล Relational ทั่วไป

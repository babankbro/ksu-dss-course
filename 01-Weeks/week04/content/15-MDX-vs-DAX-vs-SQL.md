# 15. ภาษาสำหรับการคิวรี OLAP (MDX vs DAX vs SQL)

ในขณะที่ Data Engineer ใช้ภาษา SQL ในการปั้นข้อมูล (ETL) แต่ในโลกของการ "วิเคราะห์ผ่าน OLAP" นักออกแบบจะต้องเลือกใช้ภาษาเฉพาะทางที่ถูกออกแบบมาเพื่อบวกเลขตามแกนมิติโดยเฉพาะ

## 15.1 SQL (Structured Query Language)
* **จุดเด่น:** เป็นมาตรฐานโลก ใช้ดึงข้อมูลจากตาราง 2 มิติ (แถวและคอลัมน์) 
* **จุดอ่อนใน OLAP:** เมื่อต้องดึงข้อมูลที่มีการจัดอันดับ หรือดึงยอดขายแบบ YTD (สะสมตั้งแต่ต้นปี) โค้ด SQL จะยาวเหยียด ซ้อนทับกันหลายชั้น (Subqueries) และอ่านยากมาก
* ปัจจุบันใช้เยอะกับสถาปัตยกรรม ROLAP บนคลาวด์

## 15.2 MDX (Multidimensional Expressions)
* **จุดเด่น:** ภาษาบิดาแห่งวงการ OLAP สร้างโดย Microsoft สำหรับ Cube แบบดั้งเดิม (MOLAP) 
* มันถูกออกแบบมาเพื่อ "พื้นที่หลายมิติ" โดยเฉพาะ! ในขณะที่ SQL โฟกัสไปที่ "บรรทัด" แต่ MDX โฟกัสไปที่ **"จุดตัดของเซลล์ (Tuples)"**
* **ตัวอย่าง:**
  ```mdx
  SELECT 
    { [Measures].[Net Sales] } ON COLUMNS,
    { [Time].[Year].Members } ON ROWS
  FROM [Sales Cube]
  ```
* **จุดอ่อน:** เป็นภาษาที่เรียนรู้ยากมาก (Steep learning curve) เหมือนกำลังเรียนวิชาแคลคูลัส ทำให้ความนิยมลดลงในยุคปัจจุบัน

## 15.3 DAX (Data Analysis Expressions)
* **จุดเด่น:** ภาษามาตรฐานใหม่ของวงการ Business Intelligence สมัยใหม่ (ใช้ใน Power BI และ SSAS Tabular)
* DAX เกิดมาเพื่ออุดช่องโหว่ความยากของ MDX โดยออกแบบให้หน้าตาคล้าย **"ฟังก์ชัน Excel"** ที่ชาวออฟฟิศคุ้นเคย แต่มีความทรงพลังระดับจัดการข้อมูลพันล้านบรรทัด
* **ความเก่งกาจ (Filter Context):** 
  ความลับของ DAX คือมันสามารถ "ดัดแปลงสภาพแวดล้อม (Filter Context)" ได้กลางอากาศ
  * ตัวอย่างสูตร:
    ```dax
    Total Sales 2023 = CALCULATE( SUM(Sales[Net Sales]), 'Date'[Year] = 2023 )
    ```
  * ไม่ว่าผู้ใช้จะหมุนกราฟ (Pivot) ไปท่าไหน หรือกด Drill-down ไปที่เดือนอะไร สูตรนี้จะแหกกฎการกรองบนหน้าจอ แล้วบังคับส่งยอดรวมของปี 2023 ล้วนๆ กลับมาให้เสมอ (เหมาะสำหรับเอาไว้ทำฐานตัวหารเพื่อหา % ก้อนเค้ก)

## 15.4 สรุปการเลือกใช้
* สร้างคลังข้อมูลดิบ ➔ ใช้ **SQL**
* ดึงข้อมูลจาก Cube รุ่นเก่า ➔ ใช้ **MDX**
* สร้าง Dashboard บน In-memory Model (Power BI) ➔ ใช้ **DAX**

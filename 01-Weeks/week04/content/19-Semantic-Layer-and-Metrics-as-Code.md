# 19. เลเยอร์ความหมายและ Metrics-as-Code ในบริบท OLAP

ปัญหาคลาสสิกขององค์กรคือมี Data Warehouse ที่ดีมากแล้ว แต่ผู้ใช้กลับเอาตารางดิบๆ ไปดึงบน Tableau บ้าง บน Power BI บ้าง แล้วเขียนสูตรคำนวณกำไรสุทธิด้วยตัวเอง (Logic Sprawl) ผลคือตอนประชุมปลายเดือน ตัวเลขแต่ละแผนกไม่เคยตรงกัน!

## 19.1 OLAP Semantic Layer คือคำตอบ
**Semantic Layer (เลเยอร์ความหมาย)** คือระบบที่มาคั่นกลางระหว่าง "ฐานข้อมูล" และ "หน้าจอผู้ใช้ (BI Tool)"
* แทนที่โปรแกรม BI จะยิงคิวรี SQL ดิบๆ ไปยัง Data Warehouse
* โปรแกรม BI จะยิงคำขอเป็น "ภาษามนุษย์" ไปที่ Semantic Layer (เช่น ขอ *ยอดขายสุทธิ* ตัดกับ *ภูมิภาค*)
* Semantic Layer จะมี "พจนานุกรมสูตร" ที่สถาปนิกข้อมูลนิยามเอาไว้ส่วนกลางเพียงจุดเดียว (Single Source of Truth) มันจะหยิบสูตรไปแปลเป็น SQL ที่ซับซ้อน แล้วยิงไปหาคลังข้อมูลให้เอง

## 19.2 Metrics-as-Code (มาตรวัดในรูปแบบโค้ด)
ในยุคปัจจุบัน (เช่น การใช้ `dbt Semantic Layer` หรือ `Cube.dev`) สถาปนิกจะกำหนดสูตร OLAP ทั้งหมดลงในไฟล์ข้อความ (YAML) หรือที่เรียกว่า **Metrics-as-Code**

**ตัวอย่างการนิยาม (YAML):**
```yaml
metrics:
  - name: net_revenue
    description: ยอดขายหลังหักส่วนลดและภาษี (ใช้งานทั่วบริษัท)
    type: simple
    sql: sum(sales_amount) - sum(discount_amount)
    dimensions:
      - time_date
      - customer_region
```
* **ประโยชน์สูงสุด:** 
  - หากกฎหมายภาษีเปลี่ยน บริษัทก็แค่มาแก้บรรทัด `sql` ในไฟล์นี้ที่เดียว (จุดเดียวจบ)
  - หน้าจอ Dashboard ทั้ง 1,000 หน้าของทุกแผนก จะคำนวณภาษีแบบใหม่ทันทีโดยอัตโนมัติ!
  - ไฟล์พวกนี้ถูกเก็บในระบบ Git (Version Control) ทำให้ตรวจสอบย้อนหลังได้ว่า "ใครแอบมาแก้สูตรกำไรบริษัทเมื่อวันก่อน?"

## 19.3 Headless BI (ตัดหัวกระดานชนวน)
แนวคิด Semantic Layer นำไปสู่ยุคของ **Headless BI (หรือ BI ไร้หัว)**
* BI สมัยก่อนจะทำตัวเป็น "กระเพาะ" (คำนวณเลขเอง) และ "หน้าตา" (วาดกราฟ) ในตัวเดียว
* Headless BI แยกส่วน "กระเพาะ" ไปไว้ส่วนกลาง (Semantic Layer) และให้ Tableau หรือ Power BI ลดบทบาทเป็นแค่ "หน้าตา (UI)" อย่างเดียว
* ทำให้องค์กรมีความยืดหยุ่นสูง (Decoupled) ไม่ถูกผูกมัดกับซอฟต์แวร์ยี่ห้อใดยี่ห้อหนึ่ง

# 📘 สัปดาห์ที่ 14 — ระบบผู้เชี่ยวชาญ การให้เหตุผล และการจัดการกฎทางธุรกิจ

⬅️ [[Week-13-Bayesian-Networks-and-ANFIS]] | ➡️ [[Week-15-Decision-Intelligence-and-Agentic-AI]]

## 🎯 จุดประสงค์การเรียนรู้
1. อธิบายสถาปัตยกรรมของระบบผู้เชี่ยวชาญและกลไกการอนุมานทั้งสองแบบ
2. วิเคราะห์ปัญหา Rule Explosion และ Knowledge Acquisition Bottleneck
3. เขียนตารางการตัดสินใจตามมาตรฐาน DMN พร้อมเลือก Hit Policy ให้ถูกต้อง
4. อธิบายคุณค่าเชิงวิศวกรรมของการแยกตรรกะทางธุรกิจออกจากซอร์สโค้ด

## 📖 เนื้อหาบรรยาย (2 ชม.)

### ช่วงที่ 1 (35 นาที) — ระบบผู้เชี่ยวชาญ
→ [[Expert-Systems]]
- นิยาม: สาขาคลาสสิกของ AI ที่พัฒนาขึ้นเพื่อเลียนแบบความสามารถในการใช้เหตุผลและแก้ปัญหาของผู้เชี่ยวชาญมนุษย์ในโดเมนเฉพาะทาง
- สถาปัตยกรรม:
  - **Knowledge Base** — กฎ If-Then, เฟรม (Frames), เครือข่ายความหมาย (Semantic Networks)
  - **Inference Engine** — "สมอง" ที่ประยุกต์กฎกับข้อเท็จจริงเพื่อสกัดข้อสรุป
  - **Working Memory** — ข้อเท็จจริงปัจจุบันของเคสที่กำลังพิจารณา
  - **Explanation Facility** — ชี้แจงเส้นทางการตัดสินใจ
  - **Knowledge Acquisition Subsystem** — ช่องทางนำความรู้เข้าระบบ
- กรณีคลาสสิก: **MYCIN** (วินิจฉัยการติดเชื้อในเลือด) — ทำได้ดีกว่าแพทย์ทั่วไปในบางการทดสอบ แต่ไม่เคยถูกใช้จริงในคลินิก → อภิปรายว่าเพราะเหตุใด

### ช่วงที่ 2 (25 นาที) — กลไกการอนุมาน
→ [[Inference-Engine]]

| | **Forward Chaining** | **Backward Chaining** |
|---|---|---|
| ขับเคลื่อนโดย | ข้อมูล (Data-driven) | เป้าหมาย (Goal-driven) |
| เริ่มจาก | ข้อเท็จจริงที่มี | สมมติฐาน/ข้อสรุปที่ต้องการพิสูจน์ |
| ทิศทาง | ข้อเท็จจริง → บทสรุป | เป้าหมาย → ย้อนหาหลักฐานสนับสนุน |
| เหมาะกับ | การเฝ้าระวัง การควบคุม การตรวจสอบเงื่อนไขจำนวนมาก | การวินิจฉัย การตอบคำถาม "เพราะอะไร" |
| ตัวอย่าง | ระบบแจ้งเตือนจากเซ็นเซอร์โรงงาน | ระบบวินิจฉัยอาการเสียของอุปกรณ์ |

- **Explanation Facility** คือคุณสมบัติที่ทำให้ระบบผู้เชี่ยวชาญเหนือกว่าโปรแกรมทั่วไป — สร้างความน่าเชื่อถือให้ผู้ใช้ และเป็นบรรพบุรุษของแนวคิด [[Explainable-AI-and-Governance|XAI]] ในปัจจุบัน

### ช่วงที่ 3 (30 นาที) — ข้อจำกัดและทางออกเชิงอุตสาหกรรม
- **Rule Explosion** — เมื่อโดเมนกว้างขึ้น จำนวนกฎเพิ่มแบบทวีคูณ ทำให้ระบบทำงานล่าช้า บำรุงรักษายาก และเกิดความขัดแย้งของเงื่อนไขซ้ำซ้อน
- **Knowledge Acquisition Bottleneck** — การสกัดความรู้จากผู้เชี่ยวชาญเป็นคอขวดที่แท้จริง (ผู้เชี่ยวชาญมักอธิบายไม่ได้ว่าตนตัดสินใจอย่างไร)
- ทางออกของอุตสาหกรรมซอฟต์แวร์: **BRMS (Business Rules Management Systems)** และมาตรฐาน **DMN (Decision Model and Notation)** โดย OMG → [[BRMS-and-Rule-Engines]]

### ช่วงที่ 4 (30 นาที) — มาตรฐาน DMN
→ [[DMN-Decision-Model-and-Notation]]
- เจตนา: เป็น **สะพานเชื่อมระหว่างนักวิเคราะห์ธุรกิจกับโปรแกรมเมอร์** — นักวิเคราะห์แก้กฎได้เองโดยไม่ต้องแก้โค้ด
- องค์ประกอบ:
  - **DRD/DRG (Decision Requirements Diagram/Graph)** — แผนภาพแสดงว่าการตัดสินใจใดต้องใช้ข้อมูลและการตัดสินใจย่อยใดบ้าง
  - **Decision Table** — ตารางเงื่อนไข-ผลลัพธ์
  - **FEEL** — ภาษานิพจน์มาตรฐาน

**Hit Policies ที่ต้องรู้:**

| Policy | สัญลักษณ์ | ความหมาย |
|---|:--:|---|
| Unique | U | ต้องตรงเงื่อนไขเพียงกฎเดียวเท่านั้น (ถ้าซ้อนกันถือว่าผิด) |
| Any | A | ตรงได้หลายกฎ แต่ผลลัพธ์ต้องเหมือนกัน |
| Priority | P | ตรงได้หลายกฎ เลือกตามลำดับความสำคัญของผลลัพธ์ |
| First | F | เลือกกฎแรกที่ตรงตามลำดับในตาราง |
| Collect | C | รวมผลลัพธ์ทั้งหมด (มีแบบ sum, min, max, count) |

**ตัวอย่าง Decision Table — การอนุมัติสินเชื่อ (Hit Policy: P)**

| # | รายได้ต่อเดือน | ประวัติชำระ | อายุงาน | ⇒ ผลการอนุมัติ |
|:--:|---|---|---|---|
| 1 | ≥ 50,000 | "ดี" | ≥ 2 ปี | อนุมัติ |
| 2 | [30,000..50,000) | "ดี" | ≥ 1 ปี | อนุมัติแบบมีเงื่อนไข |
| 3 | – | "เสีย" | – | ปฏิเสธ |
| 4 | < 30,000 | – | – | ส่งพิจารณาโดยเจ้าหน้าที่ |

**แพลตฟอร์มในอุตสาหกรรม:**

| แพลตฟอร์ม | คุณสมบัติหลัก | บริบทที่เหมาะสม |
|---|---|---|
| **Drools** (Red Hat / Apache KIE) | เครื่องยนต์กฎบน Java ใช้อัลกอริทึม **Rete** รองรับ DMN ขั้นสูงสุด | ประสิทธิภาพสูงมากสำหรับประเมินกฎซับซ้อนนับแสนข้อพร้อมกัน — ระบบแกนกลางทางการเงิน |
| **Camunda** | แพลตฟอร์ม BPMN ที่ผนวก DMN เข้าเป็นส่วนหนึ่งของระบบ | ยอดเยี่ยมด้าน orchestration — เหมาะกับเวิร์กโฟลว์ที่เชื่อมมนุษย์และระบบอื่นเป็นลำดับขั้น |

- 🔑 **คุณค่าเชิงวิศวกรรม:** แยก **Business logic** ออกจาก **Source code** → เปลี่ยนนโยบายได้โดยไม่ต้อง deploy ใหม่ และตรวจสอบย้อนหลังได้ (Auditability)

## 🏭 กรณีศึกษา
**อุตสาหกรรมประกันภัย — Automated Underwriting** — นักวิเคราะห์ความเสี่ยงปรับปรุงตารางกฎตามนโยบายบริษัทหรือข้อบังคับกฎหมายที่เปลี่ยนไปได้ทันทีผ่าน visual interface โดยไม่ต้องให้วิศวกรซอฟต์แวร์รื้อโครงสร้างโค้ดหลัก ทำให้ออกผลิตภัณฑ์ใหม่สู่ตลาดได้เร็ว

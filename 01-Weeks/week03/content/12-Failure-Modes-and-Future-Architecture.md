# 12. หลุมพรางทางข้อมูล และ สถาปัตยกรรมแห่งอนาคต

ในการเดินทางของข้อมูลจากระบบปฏิบัติการไปสู่รายงานการตัดสินใจ มีหลุมพรางมากมายที่พร้อมจะทำลายความน่าเชื่อถือของ DSS และนี่คือข้อผิดพลาดคลาสสิกที่พบได้บ่อย:

## 12.1 รูปแบบความล้มเหลว (Failure Modes) ที่พบบ่อย
1. **ไม่ประกาศ Grain ให้ชัดเจน:** ออกแบบตาราง Fact แบบคลุมเครือ ทำให้ยอดรวมซ้อนทับกัน
2. **เอา Transaction ผสมกับ Snapshot:** การเอาข้อมูล "ใบเสร็จ 1 ใบ" ไปยัดรวมกับตาราง "สรุปสต็อกสินค้าคงเหลือรายวัน" ทำให้คิวรีรายงานมั่วไปหมด
3. **ใช้ Natural Key ជា Dimension Key:** ฐานข้อมูลพังทันทีที่ระบบหน้าร้านอัปเดตรหัสพนักงานใหม่
4. **ปล่อยผ่านข้อมูลพัง (Data Quality ignored):** ทิ้งข้อมูลที่มีปัญหาขยะ (Rejected records) ไปโดยไม่เขียน Log ไว้ ทำให้ยอดขายในรายงานหายไปจากโลกความเป็นจริง

## 12.2 สถาปัตยกรรมแห่งอนาคต: Medallion Architecture
เพื่อรับมือกับความซับซ้อนของข้อมูลยุค AI องค์กรชั้นนำ (เช่น Databricks) ได้นำเสนอสถาปัตยกรรม **"เหรียญรางวัล (Medallion Architecture)"** ซึ่งแบ่งท่อส่งข้อมูลออกเป็น 3 โซนที่ควบคุมคุณภาพอย่างชัดเจน:

* **🥉 Bronze Layer (ดิบและเก็บหมด):**
  - กฎ: เก็บทุกอย่าง ดึงมาแบบไหนดึงลงมาแบบนั้น (Raw Data) และห้ามลบเด็ดขาด 
  - ประโยชน์: ใช้เป็นหลังพิง หากการคำนวณขั้นต่อไปผิดพลาด ก็กลับมางมข้อมูลต้นฉบับที่โซนนี้ได้
* **🥈 Silver Layer (สะอาดและพร้อมใช้):**
  - กฎ: ทำความสะอาด (Cleaned), แปลงมาตรฐาน (Standardized), และเปลี่ยนเป็น Star Schema
  - ประโยชน์: เหมาะสำหรับ Data Scientist ใช้ดึงไปทำ Machine Learning แบบอิสระ
* **🥇 Gold Layer (ธุรกิจตัดสินใจ):**
  - กฎ: ข้อมูลที่ถูก "บวกยอดรวม (Aggregated)" ให้ออกมาเป็น Business Metrics เป๊ะๆ
  - ประโยชน์: เชื่อมต่อโดยตรงเข้ากับ BI Dashboard ของผู้บริหาร (ห้ามให้ผู้บริหารไปอ่านข้อมูลโซนอื่นเด็ดขาด)

## 12.3 เช็คลิสต์ก่อนส่งมอบ Data Product สู่โปรดักชัน
ก่อนที่ Data Engineer จะประกาศว่า "รายงานตัวนี้พร้อมใช้งาน" ต้องผ่านการตรวจสอบ 5 ข้อสุดท้าย:
1. [ ] **Ownership:** ใครเป็นเจ้าของตารางนี้ หากตัวเลขผิด ใครจะตื่นขึ้นมาซ่อมตอนตี 3?
2. [ ] **Lineage:** ระบบสามารถอธิบายได้ไหมว่า ฟิลด์ `ยอดกำไร` คอลัมน์นี้ ถูกคำนวณมาจาก 3 ตารางไหนบ้าง?
3. [ ] **Idempotent Pipeline:** หากรันโค้ด ETL ซ้ำ 5 รอบ ข้อมูลจะเบิ้ล 5 เท่า หรือข้อมูลยังคงถูกทับเป็นบรรทัดเดียว (ถูกต้อง)?
4. [ ] **Latency SLA:** ถ้าตกลงกันไว้ว่า ผู้บริหารจะได้ดูยอดเมื่อวานตอน 8 โมงเช้า ระบบทำเสร็จทันเวลา 100% หรือไม่?
5. [ ] **Reconciled:** ยอดขายรวมใน Dashboard เท่ากับยอดรวมในระบบบัญชีหน้าร้านทุกสตางค์ หรือไม่?

การใช้ Medallion Architecture และเช็คลิสต์เหล่านี้ จะเปลี่ยนผ่านการทำงานจาก "การมั่วสุมข้อมูล" ให้กลายเป็น **"Data Product (ข้อมูลในฐานะผลิตภัณฑ์)"** ที่เชื่อถือได้และมีคุณภาพระดับวิศวกรรมสากล

# 18. ความปลอดภัย ความเป็นส่วนตัว และข้อกำหนดทางกฎหมายใน Data Warehouse

Data Warehouse เปรียบเสมือนเป้าหมายที่หอมหวานที่สุดของแฮกเกอร์ เพราะมันรวบรวมข้อมูลทุกอย่างจากทั้งบริษัทมาสกัดรวมกันไว้ที่เดียว การออกแบบระบบในยุคปัจจุบันจึงต้องพิจารณากฎหมายคุ้มครองข้อมูลส่วนบุคคล (PDPA/GDPR) ตั้งแต่กระดาษแผ่นแรก

## 18.1 สถาปัตยกรรมความเป็นส่วนตัวโดยกำเนิด (Privacy by Design)
เราไม่สามารถปล่อยให้ข้อมูลลูกค้ารั่วไหลเข้าไปในโซนวิเคราะห์ (Gold Layer) ได้หากไม่จำเป็น วิศวกรต้องใช้เทคนิคปกปิดตัวตน (De-identification) ระหว่างทำ ETL:

1. **Data Masking (การสวมหน้ากาก):**
   - เปลี่ยนคอลัมน์หมายเลขบัตรประชาชน `1-2345-67890-12-3` ให้เป็น `X-XXXX-XXXXX-12-3` ในตาราง Fact 
   - ให้นักวิเคราะห์เห็นแค่เลข 3 ตัวท้ายเพื่อตรวจสอบก็พอ
2. **Hashing / Tokenization:**
   - เปลี่ยนชื่อลูกค้า "นายสมชาย" ให้เป็นตัวอักษรสุ่ม เช่น `AB89XQ` 
   - หากนักวิเคราะห์ต้องการตามพฤติกรรมลูกค้าคนนี้ ก็แค่ Track รหัส `AB89XQ` ตลอดปี โดยที่นักวิเคราะห์ไม่มีทางรู้เลยว่าคนๆ นี้ชื่ออะไรในชีวิตจริง
3. **Aggregation (การกวาดรวม):**
   - แทนที่จะเก็บอายุเป็นตัวเลขเป๊ะๆ เช่น 34 ปี ให้ทำ Transformation เป็นหมวดหมู่ (Age Bucket) เช่น "ช่วงอายุ 31-40 ปี" การลดความละเอียด (Granularity) จะทำให้เดาตัวตนได้ยากขึ้น

## 18.2 Row-level Security & Column-level Security
เครื่องมือคลังข้อมูลสมัยใหม่มีฟีเจอร์การบล็อกสิทธิ์ระดับอนุภาค (Granular Access Control):
* **Column-level (ระดับคอลัมน์):** ห้ามแผนกจัดซื้อ สั่งคำสั่ง `SELECT` คอลัมน์เงินเดือนพนักงานในตารางมิติ (Dimension Table) ถ้าฝืนกดคิวรี ระบบจะตีกลับ (Access Denied)
* **Row-level (ระดับแถว):** ตารางยอดขายเดียวกัน แต่ถ้า Manager สาขากรุงเทพคิวรี ระบบจะใช้กฎแอบเติมคำสั่ง `WHERE region = 'Bangkok'` เข้าไปข้างหลังให้อัตโนมัติ ทำให้เขาเห็นยอดเฉพาะของตัวเอง 

## 18.3 กฎหมายสิทธิในการถูกลืม (Right to be Forgotten)
เมื่อลูกค้าแจ้งขอยกเลิกและให้ลบข้อมูลออกจากบริษัททั้งหมดตามกฎหมาย PDPA นี่คือฝันร้ายของ Data Warehouse:
* หากเราใช้วิธีลบ (Delete) บรรทัดยอดขายของลูกค้าคนนั้นออกจาก Fact Table ยอดขายรวมของบริษัทในรายงานผู้บริหารจะตกลงมาทันที (ซึ่งยอมรับไม่ได้)
* **วิธีแก้ (Architectural Solution):** 
  - สถาปนิกจะแยกรหัสชื่อลูกค้าและข้อมูลส่วนตัวไว้ในตาราง Dimension `Dim_Customer` 
  - ส่วนยอดขายอยู่ในตาราง `Fact_Sales` (มีแต่รหัส Surrogate Key 1234)
  - เมื่อต้องลบ เราจะไปทำลายชื่อจริงและที่อยู่ใน `Dim_Customer` ทิ้ง และเปลี่ยนชื่อเป็น "ลูกค้าที่ถูกลืม (Redacted Customer)" 
  - ผลลัพธ์: ตัวเลขยอดขายรวมยังอยู่ครบ แต่ไม่มีใครตามสืบได้อีกแล้วว่าบิลนี้ใครเป็นคนซื้อ

ความซับซ้อนของการกำกับดูแลข้อมูลเหล่านี้ เป็นเหตุผลที่ว่าทำไมระบบ Data Warehouse ถึงต้องแยกต่างหากจากระบบหน้าบ้าน

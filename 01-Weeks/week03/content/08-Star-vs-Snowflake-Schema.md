# 8. Star Schema เทียบกับ Snowflake Schema

ในการจัดเรียงตาราง Fact และ Dimension ให้อยู่ด้วยกัน มีสถาปัตยกรรมการต่อตาราง (Schema) ที่ได้รับความนิยมอยู่ 2 แบบ ซึ่งนักออกแบบต้องเลือกให้เหมาะสมกับสถานการณ์

## 8.1 Star Schema (โครงสร้างรูปดาว)
* **ลักษณะ:** มี Fact Table อยู่ตรงกลาง (เปรียบเหมือนตัวดาว) และมี Dimension Table ล้อมรอบ โดย Dimension Table ทุกตัวจะเชื่อมตรงกับ Fact Table เสมอ และไม่มีการแตกกิ่งก้านสาขาออกไปอีก
* **การออกแบบ:** เป็นการออกแบบแบบ Denormalized หมายถึง **"ยอมให้มีข้อมูลซ้ำซ้อน"**
  - ในตาราง `Dim_Product` จะมีคอลัมน์ชื่อ "หมวดหมู่สินค้า" ถ้ามีสินค้า 100 ชิ้นอยู่ในหมวดหมู่ "เครื่องดื่ม" คำว่า "เครื่องดื่ม" ก็จะถูกพิมพ์ซ้ำ 100 ครั้งในตารางนี้
* **ข้อดี:** 
  - **คอมพิวเตอร์ทำงานเร็วที่สุด:** เพราะการหาคำตอบ ต้องทำการต่อตาราง (Join) แค่ 1 จังหวะเสมอ 
  - **มนุษย์เข้าใจง่ายที่สุด:** เมื่อผู้ใช้เปิดเครื่องมือ BI (เช่น Tableau) พวกเขาจะเห็นตารางสินค้าตารางเดียวที่มีแอตทริบิวต์ครบทุกอย่างให้เลือก
* **ข้อเสีย:** เปลืองพื้นที่จัดเก็บ (แต่ปัจจุบันฮาร์ดดิสก์ราคาถูกมาก ข้อเสียนี้จึงตกไป)

## 8.2 Snowflake Schema (โครงสร้างเกล็ดหิมะ)
* **ลักษณะ:** เป็นการต่อยอดจาก Star Schema โดยนำ Dimension Table มาแตกกิ่งก้านสาขาออกไปอีก (Normalization) เพื่อลดความซ้ำซ้อน
* **การออกแบบ:** จากเดิมที่เคยมีตารางสินค้าตารางเดียว จะถูกแตกออกเป็น 3 ตาราง คือ `Dim_Product` ➔ เชื่อมไป ➔ `Dim_Subcategory` ➔ เชื่อมไป ➔ `Dim_Category` 
* **ข้อดี:**
  - **ลดความซ้ำซ้อน:** ถ้าหมวดหมู่ "เครื่องดื่ม" เปลี่ยนชื่อเป็น "เครื่องดื่มและเบเกอรี" เราแก้แค่ตาราง `Dim_Category` ที่เดียวจบ ประหยัดพื้นที่
* **ข้อเสีย:**
  - **คอมพิวเตอร์ทำงานหนัก:** หากผู้ใช้ต้องการดูยอดขายรวมหมวดหมู่ ระบบต้องทำการ Join ตารางถึง 3 จังหวะ (`Fact` ➔ `Product` ➔ `Subcategory` ➔ `Category`) ซึ่งทำให้ฐานข้อมูลประมวลผลช้าลงอย่างมาก
  - **สับสนต่อผู้ใช้งาน:** ผู้ใช้ที่ทำรายงานต้องลากเส้น Join เองหลายต่อ มักทำให้เกิดข้อผิดพลาด

## 8.3 ควรเลือกแบบไหน? (Best Practice)
ในแวดวง Data Warehouse สมัยใหม่ **"Star Schema ถือเป็นมาตรฐานทองคำ (Gold Standard)"** และได้รับความนิยมสูงสุด 
* Ralph Kimball และนักออกแบบ BI ทั่วโลกแนะนำให้ใช้ Star Schema เพราะความเร็วในการ Query และความง่ายต่อผู้ใช้ มีความสำคัญมากกว่าการประหยัดพื้นที่ฮาร์ดดิสก์
* เราจะยอมใช้ Snowflake ก็ต่อเมื่อ ลำดับชั้นของ Dimension นั้นมีความซับซ้อนมาก และมีขนาดใหญ่จริงๆ จนการปล่อยให้ข้อมูลซ้ำซ้อนทำให้ดูแลรักษาไม่ไหว หรือเครื่องมือ BI ที่ใช้อยู่บังคับให้ทำ

# 22. กลยุทธ์การสร้างคีย์ตัวแทน (Surrogate Keys) ในระบบกระจายศูนย์

ดังที่ทราบว่าใน Dimensional Modeling เราต้องสร้าง "คีย์ตัวแทน (Surrogate Keys - SK)" ขึ้นมาใหม่ให้กับตาราง Dimension ทุกตัวเพื่อความเสถียร (เช่น แทนที่จะใช้ รหัส `EMP001` เราใช้ `101`) แต่ในยุค Cloud Data Warehouse การสร้างเลข 1, 2, 3... รันไปเรื่อยๆ (Auto-increment / Identity column) กลับกลายเป็นปัญหาใหญ่

## 22.1 ทำไม Auto-increment ถึงพังในคลาวด์?
Cloud Data Warehouse (เช่น BigQuery, Snowflake) ทำงานแบบ **Distributed (กระจายศูนย์)** 
* เวลามีลูกค้าใหม่สมัครพร้อมกัน 1,000 คน เซิร์ฟเวอร์หลายสิบตัวจะแย่งกันโควต้าว่า "ใครจะได้เบอร์ 102 ไป?" 
* การมานั่งล็อคคิวแจกบัตรคิวทีละเบอร์ (Sequence Coordinator) จะทำให้คอขวดเกิดที่เซิร์ฟเวอร์กลาง และทำให้การโหลดข้อมูล (Data Load) ช้าลงอย่างมหันต์

## 22.2 การใช้ Hashing เป็น Surrogate Key
ทางแก้ที่ชาญฉลาดที่สุดในปัจจุบันคือการเลิกใช้ตัวเลขรันตามลำดับ แล้วหันมาใช้ฟังก์ชัน **Hash (แฮช)** แทน เช่น `MD5` หรือ `SHA-256`

* **วิธีการทำงาน:**
  - เมื่อมีข้อมูลลูกค้าใหม่เข้ามา เช่น รหัสธรรมชาติ `C-001` รวมกับ แหล่งข้อมูล `ERP`
  - สถาปนิกจะเอาตัวอักษรมารวมกัน: `C-001_ERP` แล้วโยนเข้าฟังก์ชัน MD5
  - จะได้ก้อนตัวอักษรประหลาดออกมา เช่น `e4d909c290d0fb1ca068ffaddf22cbd0` (นี่คือ Surrogate Key ใหม่)
* **ข้อดีมหาศาล:**
  1. **สร้างแบบกระจาย (Decentralized):** เซิร์ฟเวอร์ทั้ง 100 ตัว สามารถสร้าง Hash key ได้ด้วยตัวเองโดยไม่ต้องถามคิวใครเลย เพราะผลลัพธ์ของ Hash จะไม่ซ้ำกันอย่างแน่นอน (Collision probability ต่ำมาก)
  2. **Idempotent (รันซ้ำได้ค่าเดิม):** ถ้าท่อส่งข้อมูลพังกลางคัน แล้วเราสั่งรันโค้ด ETL ใหม่อีกรอบ `C-001_ERP` ก็จะยังคงถูกแปลงเป็น Hash ก้อนเดิมเสมอ ทำให้ไม่มีทางเกิดข้อมูลขยะเบิ้ล 2 บรรทัด (No Duplicates)

## 22.3 ข้อเสียของ Hashing
* **เปลืองพื้นที่:** Hash key (ตัวอักษร 32 ตัว) กินพื้นที่ฮาร์ดดิสก์มากกว่า Integer (ตัวเลข 4 bytes) อย่างมาก
* **ช้ากว่าเล็กน้อย:** การ Join ตารางด้วย String 32 ตัว จะช้ากว่าการ Join ด้วยตัวเลขจำนวนเต็ม

**ทางออก:** สถาปนิกในยุคคลาวด์ยอมรับข้อเสียเรื่องเปลืองพื้นที่ (เพราะ Cloud Storage ราคาถูกมาก) เพื่อแลกกับข้อดีเรื่องความเร็วในการโหลดข้อมูลและความยืดหยุ่นในการทำ Data Engineering (นี่คือหัวใจของเครื่องมือปั้นข้อมูลสมัยใหม่อย่าง dbt ที่แนะนำให้ใช้ Hash Key 100%)

# 24. กรณีศึกษา: การอพยพจากคลังข้อมูลรุ่นเก่าสู่ Cloud Lakehouse (Migration Case Study)

เพื่อสรุปเนื้อหาทั้งหมดใน Week 03 ลองพิจารณากรณีศึกษาในโลกความเป็นจริงของธนาคารขนาดใหญ่ที่ต้องตัดสินใจ "ทุบบ้านเก่า สร้างบ้านใหม่" ทางสถาปัตยกรรมข้อมูล

## 24.1 สภาพปัญหาเดิม (Legacy Architecture)
* **บ้านเก่า:** ธนาคารใช้ Data Warehouse แบบ On-premise (ตู้เซิร์ฟเวอร์ขนาดใหญ่ราคาหลายร้อยล้าน) 
* **กระบวนการ:** ทำ ETL ค่ำคืนทุกวัน โหลดข้อมูลจากระบบ Core Banking มาเก็บเป็น Star Schema
* **จุดวิกฤต:** 
  1. ข้อมูลล้นทะลัก (Storage เต็ม) และไม่สามารถขยายตู้ได้ทัน
  2. เมื่อ Data Scientist ต้องการเอา "ไฟล์เสียงการโทรเข้า Call Center" (Unstructured data) มาทำ AI วิเคราะห์อารมณ์ลูกค้า Data Warehouse เดิมเก็บไม่ได้!
  3. รายงานประจำวันเสร็จช้าลงเรื่อยๆ จาก 6 โมงเช้า กลายเป็น 10 โมงเช้า เพราะ CPU คอขวด

## 24.2 แผนการอพยพสู่ Cloud Lakehouse (The Migration Journey)
สถาปนิกข้อมูลวางแผนย้ายระบบแบบ "เปลี่ยนเครื่องยนต์ขณะบิน (Zero Downtime)" โดยใช้สถาปัตยกรรม Medallion บนระบบ Databricks (Lakehouse):

**เฟส 1: การวางรากฐาน Data Lake (Bronze Layer)**
* ย้าย Storage ทั้งหมดขึ้น Cloud (Amazon S3 / Azure Data Lake)
* ทำการดูดข้อมูลทุกอย่าง ทั้งตารางฐานข้อมูลเดิม และไฟล์เสียง Call Center ลงมากองที่โซน Bronze โดยใช้รูปแบบ ELT ดึงมาดิบๆ เก็บให้หมดด้วยราคาที่แสนถูก

**เฟส 2: การปฏิรูปการแปลงข้อมูล (Silver Layer)**
* แทนที่จะใช้โค้ด ETL เดิม ทีมงานเขียนโค้ดใหม่ด้วยเครื่องมือ **dbt** (ตามบทที่ 20) และใช้ **Spark** ประมวลผลแบบกระจาย (Distributed Compute)
* ข้อมูลตารางและการถอดไฟล์เสียงถูกนำมารวมกัน (Integration) ทำความสะอาด กลายเป็นตารางที่พร้อมให้ Data Scientist หยิบไปวิเคราะห์ความเสี่ยงลูกค้า

**เฟส 3: กลับสู่ความน่าเชื่อถือ (Gold Layer)**
* ปั้นข้อมูลให้กลับมาเป็น Star Schema (Fact และ Dimension) แบบที่ผู้บริหารธนาคารคุ้นเคย 
* การันตีคุณภาพข้อมูล (Observability - บทที่ 19) และทำ Semantic Layer (บทที่ 23) เพื่อให้ Dashboard 500 หน้าของธนาคารยังคงทำงานได้ปกติโดยไม่ต้องแก้กราฟ

## 24.3 ผลลัพธ์และบทเรียนเชิงสถาปัตยกรรม
1. **แยกส่วน (Decoupled):** ตอนนี้เมื่อธนาคารต้องการรันโมเดล AI หนักๆ ธนาคารแค่กดปุ่มเช่า CPU คลาวด์เพิ่ม 100 ตัว รันเสร็จแล้วก็คืน (ประหยัดค่าใช้จ่ายมหาศาล) และไม่กระทบความเร็วของ Dashboard รายงานยอดรวม
2. **ขยายขอบเขต:** ระบบ DSS ของธนาคารก้าวข้ามจากการใช้ตัวเลข "ยอดเงิน" มาเป็น "ความรู้สึก (Sentiment)" ได้สำเร็จ เป็นรากฐานของยุค AI 
3. **กำจัด Silo:** เลิกใช้ Data Mart ย่อยๆ ทุกคนดึงความจริงเวอร์ชันเดียว (Single Version of Truth) จาก Lakehouse แห่งนี้

กรณีศึกษานี้ตอกย้ำว่า **"Data Warehouse ไม่ใช่ซอฟต์แวร์ที่ซื้อมาติดตั้ง แต่เป็นปรัชญาและสถาปัตยกรรมการออกแบบ"** ที่มีชีวิตและวิวัฒนาการไปตามยุคสมัย

# 4. ระบบย่อยฐานความรู้ (Knowledge-based) และส่วนต่อประสานกับผู้ใช้ (User Interface)

นอกจากข้อมูลและตัวแบบแล้ว การที่จะให้คอมพิวเตอร์สนับสนุนการตัดสินใจได้อย่างสมบูรณ์แบบ มันต้องเข้าใจ "ข้อจำกัดเชิงนโยบาย" และต้อง "สื่อสาร" กับมนุษย์ให้รู้เรื่อง นี่คือหน้าที่ของอีก 2 ระบบย่อยที่เหลือ

## 4.1 ระบบย่อยการจัดการฐานความรู้ (Knowledge-Based Management Subsystem)

ความแตกต่างระหว่าง **Model** กับ **Knowledge** เป็นเรื่องที่หลายคนสับสน 
* **Model (แบบจำลอง):** พยายามพยากรณ์สิ่งที่ "น่าจะเกิดขึ้น" หรือหาทางเลือกที่ "คุ้มค่าที่สุด" (ตามสมการคณิตศาสตร์)
* **Knowledge (ความรู้):** เป็นตัวแทนของ "กฎเกณฑ์ นโยบาย ข้อจำกัด หรือความเชี่ยวชาญโดเมน" ที่องค์กรกำหนดไว้ (สิ่งที่อนุญาตให้ทำ หรือห้ามทำ)

**ทำไมถึงต้องมี Knowledge Base?**
สมมติว่า Model แนะนำว่า "ปล่อยสินเชื่อก้อนนี้แล้วจะได้กำไรสูงสุด" แต่ Knowledge Base อาจจะมีกฎระบุไว้ว่า "ห้ามปล่อยสินเชื่อให้บริษัทที่กำลังถูกฟ้องร้องคดีล้มละลาย" 
ดังนั้น Knowledge จะเข้ามาเป็น **ผู้ตรวจสอบความสมเหตุสมผล (Sanity Check) และจำกัดขอบเขต (Guardrails)** ของคำแนะนำ

**องค์ประกอบ:**
* **Rule Engine (กลไกกฎเกณฑ์):** เครื่องมือที่ใช้อ่านกฎแบบ IF-THEN-ELSE เช่น "IF อายุ < 20 THEN ต้องการเอกสารผู้ปกครอง"
* **Domain Expertise:** ความรู้เฉพาะทางที่สกัดมาจากแพทย์ ทนายความ หรืองานเฉพาะด้าน เพื่อให้ระบบสามารถ "อธิบายเหตุผล" ได้ว่า ทำไมถึงแนะนำทางเลือกนี้ (Explanation Facility)

## 4.2 ระบบย่อยส่วนต่อประสานกับผู้ใช้ (User Interface / Dialog Subsystem)

UI เป็นระบบย่อยเดียวที่ผู้ใช้งานมองเห็น หากส่วนนี้ออกแบบมาไม่ดี แม้หลังบ้านจะประมวลผลล้ำลึกแค่ไหน ระบบก็จะถูกทิ้งร้าง (Abandoned)

**หลักการออกแบบ UI ที่สนับสนุนกระบวนการคิด (Cognition Support):**
UI ของ DSS ไม่ใช่แค่ Dashboard ที่มีกราฟสีสวยงาม แต่มันต้องออกแบบมาเพื่อ "สนับสนุนกระบวนการตัดสินใจ"
1. **Separation of Fact and Fiction:** ต้องแบ่งแยกให้ชัดเจนว่า ตัวเลขไหนคือ "ข้อมูลจริงที่เกิดขึ้นแล้ว" (Fact) และตัวเลขไหนคือ "ค่าพยากรณ์จากสมมติฐาน" (Forecast/Hypothesis) ผู้ใช้ต้องไม่สับสนระหว่างสองสิ่งนี้
2. **Context and Explanation:** ทุกคำแนะนำต้องมาพร้อมบริบท เช่น "ระบบแนะนำให้สั่งซื้อสินค้า A เพิ่ม 500 ชิ้น *ความมั่นใจ 92%* เหตุผล: *เพราะพยากรณ์อากาศแจ้งว่าอุณหภูมิจะลดลง*"
3. **What-If and Drill-Down Capabilities:** ต้องมีปุ่มหรือสไลเดอร์ให้ผู้ใช้สามารถปรับพารามิเตอร์เพื่อจำลองสถานการณ์ได้ง่ายๆ (เช่น ขยับสไลเดอร์ส่วนลดจาก 5% เป็น 10% แล้วกราฟกำไรเปลี่ยนแปลงทันที)
4. **Actionable Triggers:** เมื่อเห็นข้อมูลแล้ว ต้องมีปุ่มให้กดทำสิ่งต่างๆ ต่อไปได้ เช่น:
   - **Approve (อนุมัติ):** ทำตามที่ระบบแนะนำ
   - **Override (แทรกแซง):** แก้ไขตัวเลขที่ระบบแนะนำตามวิจารณญาณมนุษย์
   - **Defer (พักเรื่องไว้ก่อน):** ขอเวลาหาข้อมูลเพิ่ม
   - **Escalate (ส่งต่อระดับสูง):** ความเสี่ยงสูงเกินไป ส่งต่อให้ผู้บริหารระดับสูงกว่าตัดสินใจ

**คำเตือนเชิงสถาปัตยกรรม:**
หากระบบ UI แสดงผลช้าเกินกว่า 3-5 วินาที กระบวนการคิด (Flow) ของผู้บริหารจะถูกขัดจังหวะ ดังนั้นนักสถาปัตยกรรมระบบต้องออกแบบระบบหลังบ้าน (Cache, In-memory DB) เพื่อให้ UI สามารถโต้ตอบได้อย่างลื่นไหลที่สุด (Low Latency Dialog)

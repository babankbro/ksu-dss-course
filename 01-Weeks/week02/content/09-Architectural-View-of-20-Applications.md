# 9. วิเคราะห์แอปพลิเคชัน DSS ระดับโลกผ่านเลนส์สถาปัตยกรรม

ในบทนี้ เราจะนำแอปพลิเคชันตัวอย่างจากสัปดาห์ที่ 1 กลับมาพิจารณาอีกครั้ง แต่คราวนี้เราจะใส่ "แว่นตาของนักสถาปนิกซอฟต์แวร์" เพื่อเจาะลึกว่า ภายใต้ฉากหน้านั้น มีระบบย่อยใดเป็นพระเอก และมีความท้าทายเชิงโครงสร้างใดบ้างที่ซ่อนอยู่

*(นี่คือ 5 ตัวอย่างเด่นจาก 20 แอปพลิเคชัน)*

## 1. Clinical Decision Support (ระบบแพทย์ช่วยวินิจฉัย)
* **ระบบย่อยเด่น:** `Knowledge Management` + `Model Management`
* **เส้นทางการตัดสินใจ:** เวชระเบียน (EHR) ➔ โมเดลความเสี่ยง (Risk Model) ➔ กฎเกณฑ์ทางคลินิก (Clinical Guideline) ➔ แพทย์วินิจฉัย
* **ประเด็นท้าทายทางสถาปัตยกรรม (Architectural Challenge):**
  - **Safety & Explainability:** การตัดสินใจเกี่ยวข้องกับความเป็นความตาย (Life-or-death) โมเดล AI ห้ามเป็นกล่องดำเด็ดขาด ระบบจะต้องลิงก์คำแนะนำกลับไปยังเปเปอร์วิจัยที่รับรอง (Document base) เพื่อให้แพทย์คลิกตรวจสอบเหตุผลได้

## 2. Fraud Detection (ระบบตรวจจับทุจริตบัตรเครดิต)
* **ระบบย่อยเด่น:** `Data Management` + `Model Management`
* **เส้นทางการตัดสินใจ:** ท่อส่งข้อมูลธุรกรรมแบบสตรีม ➔ โมเดลให้คะแนนทุจริต ➔ อนุมัติ/ระงับ/ส่งต่อมนุษย์รีวิว
* **ประเด็นท้าทายทางสถาปัตยกรรม (Architectural Challenge):**
  - **Millisecond Latency:** ต้องประมวลผลคะแนนภายในเวลาไม่เกิน 0.2 วินาทีระหว่างที่ลูกค้ารูดบัตรรออยู่ที่แคชเชียร์ หากใช้ Cloud อาจจะช้าไป จึงต้องใช้เซิร์ฟเวอร์แบบ In-memory และ Distributed nodes วางตามภูมิภาคต่างๆ

## 3. Dynamic Pricing (ระบบตั้งราคาตั๋วเครื่องบินแบบพลวัต)
* **ระบบย่อยเด่น:** `Model Management` + `Knowledge Management`
* **เส้นทางการตัดสินใจ:** ข้อมูลค้นหาของลูกค้า ➔ โมเดล Demand-Supply ➔ ราคาใหม่ ➔ ตีพิมพ์ลงเว็บ
* **ประเด็นท้าทายทางสถาปัตยกรรม (Architectural Challenge):**
  - **Guardrails:** อัลกอริทึมมักมีความโลภ (Greedy) มันอาจขึ้นราคาตั๋วเครื่องบินตอนเกิดภัยพิบัติเป็น 10 เท่า ซึ่งจะส่งผลให้แบรนด์พังทลาย ดังนั้น Knowledge Base ต้องสร้างกฎ "ขอบเขตเพดานราคา (Price Caps)" ล็อกเอาไว้ไม่ให้โมเดลรันคำสั่งออกไปสู่ลูกค้า

## 4. Disaster Response (ศูนย์บัญชาการภัยพิบัติ)
* **ระบบย่อยเด่น:** `Communication-driven` + `Data Management`
* **เส้นทางการตัดสินใจ:** แหล่งข้อมูลกระจัดกระจาย (โซเชียลมีเดีย, โดรน, เซ็นเซอร์) ➔ ภาพรวมสถานการณ์เดียวกัน (Common picture) ➔ คณะกรรมการออกคำสั่ง
* **ประเด็นท้าทายทางสถาปัตยกรรม (Architectural Challenge):**
  - **Resilience:** เมื่อเกิดภัยพิบัติ เสาสัญญาณอินเทอร์เน็ตอาจล่ม ระบบ DSS แบบพึ่งพา Cloud 100% จะตายทันที สถาปัตยกรรมจึงต้องรองรับการทำงานแบบออฟไลน์ (Offline-first) ในศูนย์พักพิง และซิงค์ข้อมูลทีหลัง

## 5. Workforce Scheduling (ระบบจัดตารางพนักงาน)
* **ระบบย่อยเด่น:** `Model Management`
* **เส้นทางการตัดสินใจ:** พยากรณ์อุปสงค์ลูกค้า + ข้อจำกัดเรื่องทักษะพนักงาน ➔ Solver รันการจัดตาราง ➔ ผู้จัดการกะอนุมัติ
* **ประเด็นท้าทายทางสถาปัตยกรรม (Architectural Challenge):**
  - **Human Constraints (ข้อจำกัดความเป็นมนุษย์):** โมเดล Optimizer อาจจัดให้พนักงานทำงาน 2 วันแล้วหยุด 1 วัน สลับไปมาจนเหนื่อยล้า สถาปัตยกรรมของโมเดลนี้ต้องเปิดช่องให้มนุษย์ (ผู้จัดการ) ปรับแก้ด้วยมือ (Manual Override) เพื่อเพิ่มความยืดหยุ่นทางอารมณ์และคำขอลากิจ

การถอดรหัสแอปพลิเคชันเหล่านี้ ช่วยให้นักศึกษาสามารถคาดเดา **จุดเปราะบาง (Vulnerabilities)** ของระบบไอทีในองค์กร และเตรียมวิธีรับมือไว้ได้ก่อนที่มันจะล่มสลาย

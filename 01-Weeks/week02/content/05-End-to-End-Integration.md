# 5. การทำงานร่วมกันแบบ End-to-End (End-to-End Integration)

เพื่อให้เห็นภาพว่าระบบย่อยทั้ง 4 ส่วน (Data, Model, Knowledge, UI) ประกอบร่างและทำงานร่วมกันอย่างไร เราจะใช้ **"ระบบสนับสนุนการอนุมัติสินเชื่อ (Credit Approval DSS)"** ของธนาคารแห่งหนึ่งเป็นกรณีศึกษา

## 5.1 สถานการณ์จำลอง
นายสมชาย ยื่นขอสินเชื่อธุรกิจ 10 ล้านบาทเพื่อขยายโรงงาน เจ้าหน้าที่สินเชื่อ (ผู้ใช้งานระบบ) เปิดหน้าจอ DSS ขึ้นมาเพื่อพิมพ์รหัสประชาชนของนายสมชายเข้าสู่ระบบ สิ่งที่เกิดขึ้นหลังบ้านภายในเวลา 2 วินาที มีดังนี้:

## 5.2 การทำงานของแต่ละระบบย่อย

**1. Data Management Layer (การรวบรวมข้อเท็จจริง)**
- ทันทีที่รับรหัสประชาชน ระบบจัดการข้อมูลจะส่งคำสั่ง (Query) ไปดึงข้อมูลจากระบบภายในธนาคาร (ประวัติการฝากเงิน, หนี้คงค้าง) และยิง API ออกไปยังเครดิตบูโร (External Data) เพื่อดึงประวัติการชำระหนี้ 
- ข้อมูลที่ได้มาดิบๆ จะถูกแปลง (Transform) ให้เป็น Format มาตรฐานที่พร้อมคำนวณ

**2. Model Management Layer (การสร้างภาพพยากรณ์)**
- ข้อมูลที่แปลงแล้วจะถูกส่งเข้าสู่ **Credit Risk Model** (เช่น อัลกอริทึม Logistic Regression หรือ Random Forest) 
- ตัวแบบจะคำนวณว่า "Probability of Default (โอกาสหนี้สูญ) ของนายสมชายเท่ากับกี่เปอร์เซ็นต์" 
- และใช้ Financial Model คำนวณหา Expected Loss (ความเสียหายที่คาดหวัง) หากต้องตั้งสำรองหนี้

**3. Knowledge-Based Management Layer (การตรวจทานด้วยกฎ)**
- ระบบไม่ได้เชื่อ Model เพียงอย่างเดียว มันส่งผลลัพธ์ไปเทียบกับ นโยบายสินเชื่อของธนาคาร และ กฎหมายของธนาคารแห่งประเทศไทย
- *ตรวจสอบกฎ:* "หากหลักทรัพย์ค้ำประกันเป็นที่ดินตาบอด ห้ามอนุมัติวงเงินเกิน 5 ล้านบาท" 
- แม้ Model จะบอกว่าความเสี่ยงต่ำ แต่ Knowledge Base ตรวจพบว่าหลักทรัพย์เป็นที่ดินตาบอด ระบบจึงบีบกรอบคำแนะนำ (Constrain the recommendation)

**4. User Interface Layer (การนำเสนอและการตัดสินใจ)**
- หน้าจอ Dashboard จะแสดงผลขึ้นมาให้เจ้าหน้าที่สินเชื่อเห็น:
  - **ภาพรวมข้อมูล (Data):** แสดงประวัติทางการเงินของลูกค้า
  - **ผลจากโมเดล (Model):** "ความเสี่ยงระดับ ปานกลางค่อนข้างต่ำ (Probability of Default 4%)"
  - **คำแนะนำที่ผ่านกฎแล้ว (Knowledge):** "แนะนำให้อนุมัติ แต่จำกัดวงเงินสูงสุดที่ 5 ล้านบาท (เนื่องจากกฎระเบียบเรื่องที่ดินตาบอด)"
- **มนุษย์ตัดสินใจ (Human Decision):** เจ้าหน้าที่สามารถคลิกเข้าไปดูเหตุผล (Explainability) ทำการปรับลดดอกเบี้ย (What-if) หรือถ้าเจ้าหน้าที่มีเอกสารยืนยันว่าที่ดินนั้นกำลังจะมีการตัดถนนผ่าน (ข้อมูลที่ระบบไม่รู้) เจ้าหน้าที่สามารถกดปุ่ม **Override** กฎข้อนั้น และพิมพ์เหตุผลกำกับเพื่ออนุมัติวงเงิน 10 ล้านบาทได้
- **บันทึกผลและเรียนรู้ (Outcome & Feedback):** ไม่ว่าเจ้าหน้าที่จะอนุมัติหรือปฏิเสธ ผลการกระทำและเหตุผลจะถูกบันทึกกลับลงไปใน Data Warehouse เพื่อใช้เป็นข้อมูลฝึกสอน (Training Data) ให้กับ Model ในรอบปีถัดไป

## 5.3 จุดตรวจสอบ (Checkpoints) ที่ขาดไม่ได้ในกระบวนการนี้
เพื่อให้สถาปัตยกรรมทำงานอย่างสมบูรณ์ ไร้ข้อกังขา สถาปนิกต้องฝังจุดตรวจสอบไว้ใน Workflow:
- **Data Freshness:** หน้าจอต้องระบุว่า ดึงข้อมูลบูโรมาเมื่อ "วันนี้ เวลา 10:00 น."
- **Model Version:** ระบุว่าคะแนนนี้ประเมินโดย "Risk Model v2.4"
- **User Identity:** ใครเป็นคนล็อกอินเข้ามาวิเคราะห์
- **Rationale Capture:** หากมีการ Override เจ้าหน้าที่ต้องถูกบังคับให้พิมพ์เหตุผลเสมอ

การร้อยเรียงระบบทั้ง 4 เข้าด้วยกันอย่างแนบเนียน คือศิลปะขั้นสูงสุดของการพัฒนาระบบ DSS ที่จะช่วยให้องค์กรก้าวข้ามข้อจำกัดของมนุษย์ได้อย่างยั่งยืน

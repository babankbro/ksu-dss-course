# 7. ทางเลือกเชิงสถาปัตยกรรมและข้อแลกเปลี่ยน (Architectural Choices & Trade-offs)

ในการสร้างระบบสนับสนุนการตัดสินใจ สถาปนิกไม่มีคำว่า "ดีที่สุดแบบสมบูรณ์" (No Silver Bullet) มีเพียง "ความเหมาะสมกับข้อจำกัด" การเลือกสถาปัตยกรรมใดๆ มักต้องแลกมาด้วยข้อเสียอีกด้านหนึ่ง (Trade-offs) เสมอ

## 7.1 Batch Processing เทียบกับ Real-Time Processing
การเลือกว่าโมเดลจะประมวลผลข้อมูลเมื่อใด:
* **Batch Processing (การประมวลผลเป็นกลุ่มรอบ):** 
  - **ลักษณะ:** รวบรวมข้อมูลไว้แล้วประมวลผลพร้อมกันในเวลากลางคืน เช่น รัน Forecast ยอดขายทุกตี 2
  - **ข้อดี:** ประหยัดค่าเซิร์ฟเวอร์ ต้นทุนต่ำ ตรวจสอบย้อนหลังง่าย ไม่กระทบระบบหน้าร้าน
  - **ข้อเสีย:** ข้อมูลที่ผู้บริหารเห็นตอนบ่าย 3 คือข้อมูลของเมื่อวาน (Stale data)
  - **เหมาะกับ:** การวางแผนระยะกลาง-ยาว เช่น การวางแผนยอดสั่งผลิตรายสัปดาห์

* **Real-time Processing (การประมวลผลทันที):**
  - **ลักษณะ:** ข้อมูลเข้าสู่ระบบปุ๊บ ประมวลผลและแสดงผลปั๊บ 
  - **ข้อดี:** ทันต่อเหตุการณ์ (Value of information ลดลงรวดเร็ว) เช่น ตรวจจับการทุจริต หรือระบบจราจรอัจฉริยะ
  - **ข้อเสีย:** ค่าใช้จ่ายสูงมาก (High cost) ต้องลงทุนระบบ Streaming (เช่น Apache Kafka) และเสี่ยงล่มสูง (High Availability constraints)

## 7.2 Cloud เทียบกับ Edge Computing
* **Cloud Computing (ศูนย์ข้อมูลส่วนกลางผ่านอินเทอร์เน็ต):**
  - **ข้อดี:** มีพลังประมวลผลไม่จำกัด (Scalable), รวบรวมข้อมูลจากทุกสาขามาวิเคราะห์แบบ Holistic view ได้ง่าย
  - **ข้อเสีย:** มีความหน่วง (Latency) ในการรับส่งข้อมูลผ่านอินเทอร์เน็ต หากเน็ตตัด ระบบ DSS จะใช้งานไม่ได้เลย
* **Edge Computing (ประมวลผลที่จุดเกิดเหตุ):**
  - **ข้อดี:** รวดเร็วมากระดับเสี้ยววินาที เช่น ชิป AI ในกล้องวงจรปิดของระบบเตือนภัย ทำงานได้แม้เครือข่ายขาด และช่วยปกป้องข้อมูลส่วนบุคคล (Privacy)
  - **ข้อเสีย:** พลังประมวลผลต่ำกว่ามาก ไม่สามารถรันโมเดลที่ซับซ้อนใหญ่ๆ ได้
* **Hybrid (ลูกผสม):** เป็นทางเลือกที่นิยมที่สุด คือใช้ Edge เพื่อประมวลผลและตัดสินใจเรื่องเฉพาะหน้าแบบด่วน (เช่น เซ็นเซอร์เบรกฉุกเฉิน) และส่งข้อมูลสรุปกลับไปหา Cloud เพื่อฝึกโมเดล (Retrain Model) ให้เก่งขึ้น

## 7.3 Centralized เทียบกับ Distributed Architecture
* **Centralized (รวมศูนย์):**
  - Data Warehouse และ Model อยู่ที่ส่วนกลางที่เดียว
  - **ข้อดี:** บริหารจัดการความปลอดภัยง่าย ข้อมูลเป็นมาตรฐานเดียว (Single Source of Truth) ผู้บริหารเห็นภาพรวมทั้งองค์กร
  - **ข้อเสีย:** หากเซิร์ฟเวอร์กลางล่ม สาขาทุกสาขาจะทำงานไม่ได้
* **Distributed / Microservices (กระจายศูนย์):**
  - หั่นระบบ DSS เป็นเซอร์วิสเล็กๆ แยกกัน (เช่น AI พยากรณ์ยอดขายอยู่เซิร์ฟเวอร์นึง, ระบบจัดการสต็อกอยู่อีกเซิร์ฟเวอร์นึง)
  - **ข้อดี:** มีความยืดหยุ่นสูง (Resilience) และให้อำนาจแต่ละแผนกดูแลโมเดลของตัวเอง (Autonomy)
  - **ข้อเสีย:** ระบบซับซ้อน มักเกิดปัญหาเวอร์ชันโมเดลไม่ตรงกัน หรือข้อตกลงและกฎเกณฑ์การตัดสินใจที่ขัดแย้งกันข้ามแผนก (Conflict resolution is hard)

**บทสรุป:** หน้าที่ของสถาปนิกคือการถามผู้ใช้ว่า "ในกรณีวิกฤต คุณยอมสละความแม่นยำเพื่อแลกกับความรวดเร็วหรือไม่?" เพื่อหาจุดสมดุลของสถาปัตยกรรม

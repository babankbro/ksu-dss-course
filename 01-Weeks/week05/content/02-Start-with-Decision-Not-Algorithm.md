# 2. เริ่มต้นที่การตัดสินใจ ไม่ใช่อัลกอริทึม (Decision First, Algorithm Later)

ความล้มเหลวที่คลาสสิกที่สุดของโปรเจกต์ Data Science คือการที่นักวิเคราะห์รีบเปิดโปรแกรม (เช่น Jupyter Notebook) แล้วเขียนโค้ดรันโมเดล AI ทันที โดยที่ยังไม่ได้นิยามปัญหาทางธุรกิจให้ขาด 

ในบริบทของ DSS เราต้อง "เริ่มจากจุดจบ" เสมอ นั่นคือการถามว่า **"ผลลัพธ์จากโมเดลนี้ จะถูกนำไปให้ใครใช้ตัดสินใจทำอะไร?"**

## 2.1 คำถาม 7 ข้อ ก่อนเริ่มทำ Data Mining
ก่อนจะเริ่มเขียนโค้ดบรรทัดแรก ทีมงานจะต้องหาคำตอบ 7 ข้อนี้ให้ได้:

1. **ใครคือผู้ใช้ผลทำนาย (End User)?:** 
   - โมเดลนี้ส่งให้ "พนักงานอนุมัติสินเชื่อ" หรือส่งให้ "พนักงานการตลาด"? ภาษาที่ใช้แสดงผลบนจอจะต้องต่างกัน
2. **ต้องตัดสินใจอะไร และ ภายในเวลาเท่าใด (Action & Latency)?:** 
   - อนุมัติบัตรเครดิตต้องตัดสินใจภายใน 2 วินาที (โมเดลต้องเร็วและเบา) 
   - จัดแคมเปญส่งอีเมลประจำเดือน มีเวลาคิด 3 วัน (โมเดลซับซ้อนแค่ไหนก็ได้)
3. **หน่วยที่ถูกจำแนก (Grain) คืออะไร?:** 
   - เรากำลังทำนาย "รายบุคคล (Customer_ID)", หรือทำนาย "รายธุรกรรม (Transaction_ID)"?
4. **เป้าหมาย (Target) ถูกนิยามเมื่อใด?:** 
   - คำว่า "หนี้สูญ (Default)" หมายถึงอะไร? ค้างจ่าย 1 วันนับไหม? หรือต้องค้างเกิน 90 วัน? (ต้องมีนิยามที่เป๊ะมากทางกฎหมาย)
5. **ข้อมูลใดมีอยู่จริง ณ เวลาที่ทำนาย (Time of Prediction)?:** 
   - ห้ามเอาข้อมูลในอนาคตมารวมเด็ดขาด (เดี๋ยวจะกล่าวถึงในบท Data Leakage)
6. **ต้นทุนของการทายผิด (Cost of False Positives & False Negatives):** 
   - ถ้าโมเดลทายผิดว่าลูกค้าเป็นโจร (ทั้งที่เขาเป็นคนดี) ลูกค้าจะด่าบริษัทเราหนักแค่ไหน? เรายอมรับความเสี่ยงนี้ได้กี่เปอร์เซ็นต์?
7. **ใครมีสิทธิ์ขัดขืนโมเดล (Override Authority)?:** 
   - ถ้าโมเดลสั่งปฏิเสธสินเชื่อ แต่ผู้จัดการสาขาอยากจะให้ผ่าน ผู้จัดการมีสิทธิ์กด Override บนระบบ DSS ไหม? และถ้าทำได้ ต้องให้เขาพิมพ์เหตุผลบันทึกไว้ในฐานข้อมูลเสมอ

## 2.2 ตัวอย่างการนิยามปัญหาที่คมคาย
* **นิยามที่แย่ (หลวมเกินไป):** "สร้างโมเดลคาดการณ์ลูกค้าผิดนัดชำระหนี้"
* **นิยามที่ดี (คมและชัดเจน):** "สร้างโมเดลคาดการณ์ ณ วินาทีที่ลูกค้ากดปุ่ม Submit เพื่อทำนายว่า ลูกค้าคนนี้จะค้างชำระหนี้เกิน 30 วัน ภายในระยะเวลา 90 วันหลังอนุมัติหรือไม่ เพื่อให้พนักงานสินเชื่อกดอนุมัติหรือเรียกเอกสารเพิ่ม"

การนิยามที่เป๊ะ จะทำให้นักทำเหมืองข้อมูล (Data Miner) สามารถไปดึงข้อมูลใน Data Warehouse มาปั้นได้ตรงจุด และไม่สร้างโมเดลที่ทายเก่งแต่ไม่มีใครกล้าเอาไปใช้จริง

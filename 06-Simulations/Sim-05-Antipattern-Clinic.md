# 🩺 Sim 05 — Anti-pattern Clinic

> เปิดที่ `http://localhost:3000/sims/antipattern-clinic`

## จุดประสงค์
เปลี่ยน anti-pattern 7 ข้อจาก "รายการที่อ่านแล้วพยักหน้า" ให้เป็น "ทักษะการวินิจฉัยที่ใช้ได้จริง"
โดยให้ผู้เรียนตรวจระบบผู้ป่วย 8 ราย จากอาการ หน้าจอจริง และตัวชี้วัด

## กลไก
แต่ละเคสมี 3 ขั้น: **วินิจฉัย → สั่งยา → ดูผลการรักษา**
คะแนนมี 3 มิติ — วินิจฉัยถูกหรือไม่ · ยาที่ควรสั่งแต่ไม่ได้สั่ง · **ยาที่สั่งเกินความจำเป็น**

> [!warning] เคสที่ 8 เป็นกับดักโดยเจตนา
> เป็นระบบสนับสนุนการจัดเตียงผู้ป่วยที่ **ออกแบบมาดีอยู่แล้ว** คำตอบที่ถูกคือ "ไม่พบความผิดปกติ"
> และยาที่ควรสั่งคือ **ไม่ต้องสั่งอะไรเลย** · นักศึกษาส่วนใหญ่จะพยายามหาโรคให้เจอ
> ใช้จังหวะนี้อภิปรายว่าการ over-engineer ระบบที่ทำงานดีอยู่แล้ว
> คือความล้มเหลวเชิงสถาปัตยกรรมที่พบบ่อยพอๆ กับการทำน้อยเกินไป

## เฉลยทั้ง 8 เคส (สำหรับผู้สอน)

| # | ระบบผู้ป่วย | โดเมน | คำวินิจฉัย | ยาที่ถูกต้อง |
|:--:|---|---|---|---|
| 1 | ระบบติดตามยอดขายสาขา | ค้าปลีก | **Dashboard-only DSS** | เพิ่มทางเลือกและปุ่มสั่งการ |
| 2 | ระบบคัดกรองใบสมัครงาน | ทรัพยากรบุคคล | **Model as Oracle** | แสดงเหตุผล + แสดงความไม่แน่นอน |
| 3 | ระบบแนะนำซื้อขายหลักทรัพย์ | การเงิน | **Stale-data Certainty** | แสดงความสดของข้อมูลและเตือนเมื่อค้าง |
| 4 | ระบบคำนวณส่วนลดลูกค้า | ค้าปลีก | **Rule Spaghetti** | ย้ายเข้า rule engine + กำหนดเจ้าของกฎ |
| 5 | ระบบยกเว้นค่าปรับลูกค้า | โทรคมนาคม | **Untraceable Decision** | บันทึกการตัดสินใจ + เก็บ lineage และเหตุผล |
| 6 | ระบบยืนยันตัวตนเปิดบัญชี | ธนาคาร | **Automation without Exit** | ออกแบบเส้นทางสำรอง + เพิ่มจุดมนุษย์อนุมัติ |
| 7 | ระบบแนะนำปริมาณสั่งซื้อ | ซัพพลายเชน | **Feedback Blindness** | เก็บผลลัพธ์จริง + เฝ้าระวัง drift |
| 8 | ระบบจัดเตียงผู้ป่วย | โรงพยาบาล | **ไม่พบความผิดปกติ** | — (ไม่ต้องรักษา) |

## เคสที่มักตอบผิด

- **เคสที่ 1** มักถูกวินิจฉัยเป็น "Feedback Blindness" เพราะเห็นว่าไม่มีวงจรป้อนกลับ —
  แต่อาการหลักคือ **ไม่มีทางลงมือทำจากในระบบ** ผู้ใช้จึงเลิกเข้าไปดู
  ให้ชี้ที่ตัวชี้วัด "การตัดสินใจที่เกิดขึ้นในระบบ = 0" ซึ่งเป็นลายเซ็นเฉพาะของ Dashboard-only
- **เคสที่ 3 กับ 7** สับสนกันบ่อย ทั้งคู่เกี่ยวกับ "ข้อมูลไม่ตรงความจริง" —
  แต่เคส 3 คือ**ข้อมูลนำเข้า**ล้าสมัย ส่วนเคส 7 คือ**โมเดล**ล้าสมัยเพราะไม่เคยวัดผลย้อนหลัง
  คนละชั้นของสถาปัตยกรรม จึงคนละวิธีรักษา
- **เคสที่ 5 กับ 6** ทั้งคู่มีคำว่า "มนุษย์" — เคส 5 มนุษย์แทรกแซงได้แต่ไม่มีร่องรอย (governance)
  เคส 6 มนุษย์แทรกแซง**ไม่ได้เลย** (availability) ต่างกันคนละคุณลักษณะคุณภาพ

## ขั้นตอนปฏิบัติ (40 นาที)

1. **(25 นาที)** เดินครบทั้ง 8 เคส บันทึกคำวินิจฉัยและยาที่สั่งของตนเองไว้ก่อนกดยืนยันทุกครั้ง
2. **(15 นาที)** ตอบคำถามใบงาน

## คำถามในใบงาน

1. บันทึกคะแนน 3 มิติของตนเอง — ถ้า "ยาเกิน" สูงกว่า "ยาขาด"
   บอกอะไรเกี่ยวกับนิสัยการออกแบบระบบของคุณ
2. เคสใดที่คุณวินิจฉัยผิด? อาการใดที่ทำให้เข้าใจผิด และอาการใดคือ**ลายเซ็นที่แท้จริง**
   ของ anti-pattern นั้น
3. เคสที่ 8 คุณสั่งยาไปกี่รายการ? ถ้าสั่งเกิน 0 จงประเมินว่าในโลกจริง
   การเพิ่มองค์ประกอบเหล่านั้นจะสร้างต้นทุนและความเสี่ยงอะไรเพิ่มขึ้นบ้าง
4. จับคู่ anti-pattern ทั้ง 7 ข้อเข้ากับ **ระบบย่อยของ DSS** ที่บกพร่อง
   (Data / Model / Knowledge / UI / Governance) — มีข้อใดที่ข้ามหลายระบบย่อยบ้าง
5. ยกตัวอย่างระบบจริงที่คุณเคยใช้ (แอปธนาคาร ระบบทะเบียนนักศึกษา แอปสั่งอาหาร ฯลฯ)
   ที่มีอาการของ anti-pattern อย่างน้อย 1 ข้อ พร้อมระบุอาการที่สังเกตได้
   และเสนอการรักษาที่ตรงและน้อยที่สุด
6. เลือก anti-pattern 1 ข้อ แล้วอธิบายว่าเหตุใดมันจึง **ไม่ใช่บั๊ก** —
   กล่าวคือระบบทำงานตามที่เขียนโค้ดไว้ทุกประการ แต่ยังล้มเหลว

## แนวคำตอบข้อ 4 (สำหรับผู้สอน)

| Anti-pattern | ระบบย่อยที่บกพร่อง |
|---|---|
| Dashboard-only DSS | UI (ขาด action loop) + Model (ไม่มีการสร้างทางเลือก) |
| Model as Oracle | UI (ไม่อธิบาย) + Model (ไม่รายงานความไม่แน่นอน) |
| Stale-data Certainty | Data (ไม่ตรวจความสด) + UI (ไม่สื่อสารสถานะ) — **ข้ามสองชั้น** |
| Rule Spaghetti | Knowledge (ไม่มีเวอร์ชันและเจ้าของ) |
| Untraceable Decision | Governance (ไม่มี lineage) |
| Automation without Exit | ทั้งระบบ — เป็นความบกพร่องของ **การจัดสรรอำนาจตัดสินใจ** ไม่ใช่ของชั้นใดชั้นหนึ่ง |
| Feedback Blindness | Feedback loop (ไม่มีการวัดผลย้อนหลัง) |

> ประเด็นที่ควรดึงออกมา: anti-pattern ส่วนใหญ่ **ไม่ได้อยู่ในกล่องใดกล่องหนึ่ง แต่อยู่ที่เส้นเชื่อมระหว่างกล่อง**
> ซึ่งเป็นเหตุผลที่แผนภาพสถาปัตยกรรมต้องระบุสัญญาของเส้นเชื่อม ไม่ใช่แค่ชื่อกล่อง
